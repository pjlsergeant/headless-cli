# One Day

Known non-show-stopper issues in process lifecycle handling, kept for later.

- Ctrl-Z: the agent's own session makes its group orphaned, so a forwarded SIGTSTP (the `suspendHandler` in `executeCommand`) is discarded by the kernel for agents without a SIGTSTP handler.
- New-session and double-fork escapes: descendants that leave via a new session and are reparented before headless looks are not cleaned up. Verified: Claude Code's Bash tool starts commands in a new session. Same for setsid, `tmux new-session -d`, pm2. Possible fix: a Linux subreaper supervisor (`PR_SET_CHILD_SUBREAPER`) so orphans reparent to headless.
- Window between `spawn()` and the `HEADLESS_AGENT_PGID_FILE` write in `executeCommand` (`agent.pgid`): a SIGKILL of headless there (or a failed write) leaves the agent's group unknown to cron.
- A signal inside the billing/retry wrapper after an attempt finishes but before `runWithBilling` returns (the `runWithBilling` call in `runCli`) still ends headless immediately, skipping wrap-up.
- Node drops queued stdout data on exit when stdout is a socket pair (Node `spawn` pipes) and the reader is slow; affects Node consumers of `--sdk-format ndjson`, not real pipes (Python SDK).
- Docker runs only clean up the host-side `docker` client tree; processes the agent leaves inside the container are not touched.
- Modal runs: post-exit cleanup and `--keep-background` are no-ops (the agent runs remotely).
- Async run messages (`run message --async`) always clean up the node's tree; a node's stored `--keep-background` is ignored there (`sweep()` in `src/async-run-message.ts`).
- Run and node store locks (`src/run-storage.ts`) still use proper-lockfile's mtime staleness: two waiters that both see a stale lease can both reclaim it. Not moved onto `src/owner-lock.ts` because node locks hand ownership to another process tree and judge liveness by that tree, which the owner lock does not model.
- Lock directories (`~/.headless/launch-locks/<key>`, `cron/locks/jobs/<id>`) are never removed, by design (removing one would break atomic reclaim); `cron rm` leaves its small lock directory behind.
- Lock holders headless cannot probe can wedge or misjudge a lock (`src/owner-lock.ts` host check): holders on another host (shared filesystem) count as alive indefinitely, so a crashed remote holder needs its lock directory removed by hand; a container started outside headless (so without `HEADLESS_IN_CONTAINER=1`) that mounts `~/.headless` can still take, and on dying wedge, the cron daemon lock or a Docker session lock, which have no maximum hold time; and two containers sharing a volume with the same explicitly set hostname and overlapping PIDs can misjudge a live lock holder as stale.
- A Docker session's store lock lives in the container-writable session home, so the container can make that session's store writes time out.
- The session store drops records that fail validation the next time it is written (now for the local store too, not only Docker session stores).
- Cron reconcile can mark an execution `killed`/`stale` when the post-exit sweep of its agent group outlasts a daemon tick, though it had finished normally.
- A daemon tick already in progress at shutdown can start an execution after the shutdown kill passed that job; the next daemon's reconcile cleans it up.
- `cron stop` sends SIGTERM and returns without waiting for the daemon to exit.
- The Docker session lock is acquired before the wrap-up guard is installed (`src/cli.ts` `acquireDockerSessionLock` vs `installWrapUpGuard`), so a signal in that window skips its release; the holder is on the host, so the lock is reclaimable, not wedged.
- Locks with a maximum hold (session store, cron jobs: 60s; launch: 10 min or `--timeout` + 1 min) can be taken over from a holder that is alive but slower than that. Sections check `held()` before each write, which leaves only the window between that check and the rename; a tmux claim with no `--timeout` that takes over 10 minutes can be overtaken and lose transcript attribution.
- Flaky under full-suite load (timing-sensitive; each failed once in a full run and passes alone): "Antigravity usage overlay ... SIGTERM handler" (tests/headless.test.ts, also passes in later full runs) and "cron daemon keeps its signal handlers until active executions are killed" (tests/cron.test.ts).
- Docker launch options (`--docker-image`, `--docker-arg`, `--docker-env`) are not persisted per node, so a host-side `run message` to a Docker or Modal node is refused instead of relaunching it in its sandbox; only a running Docker node's mailbox can start one (with its own flags).
- Nodes a container starts through its mailbox are detached and outlive the requesting container, like host `run message --async`; nothing stops them when the orchestrator exits without `run wait`.
- Explicit `--docker-env NAME=value` entries are handed to nodes started from a mailbox on the detached child's argv (visible in `ps`), as they already were for the original invocation.
- A container can leave dot-prefixed files in its mailbox `requests/` (treated as in-progress writes), using disk in the run dir until that launch directory is swept.
- Two concurrent launches of the same Docker run node get separate mailbox directories; a later launch may sweep the other's directory while it is still polling. (Concurrent launches of one node are already unsupported.)
- User-supplied `--docker-arg` volume mounts are not checked for overlap with Headless state.
- Attacker-filled old mailbox launch directories can linger: the bounded best-effort sweep on the next launch does not recurse into subdirectories a container nested inside its mailbox.
- Prompts starting with "-" are still passed as a bare positional (or `-p` value) to Cursor (`agent`, one-shot and interactive), OpenCode (`run` and interactive run), Pi (one-shot and interactive), Gemini interactive, and Antigravity (`agy -p`); none of these CLIs is installed here to verify whether they accept `--` or a dash-leading value, and none has a stdin prompt path in Headless. Claude, Codex and Gemini one-shot are fixed; Gemini one-shot now sends inline prompts on stdin with `--prompt ''` (the path prompt files already used), not verified against an installed gemini.
- Modal sandbox lifetime is counted from sandbox creation (agent timeout + 120s recovery window), so a slow upload eats into the recovery window.
- `--modal-keep-sandbox` creates the sandbox with a 24h lifetime for every run, so if Headless itself is SIGKILLed the sandbox bills up to 24h instead of the agent timeout.
- The kept-sandbox message points at the Modal dashboard or the JS SDK to terminate; Headless has no command to terminate (or fetch from) a kept sandbox.
- ACP SDK logs "Error handling request" to stderr for each refused ACP file read (SDK console logging of handler errors).
- ACP `fs/read_text_file` ignores the request's `line`/`limit` and returns the whole file.
- `--docker --print-command` prints an AWS mount source in a staged temp dir that is removed when Headless exits, so the printed command is not runnable as is when `AWS_PROFILE` is forwarded.
- The staged Docker AWS credentials temp dir is left behind if Headless is killed without running its cleanup (e.g. SIGKILL).
- AWS profile staging copies the SSO token cache file but not the SSO client registration cache, so an expired SSO token cannot be refreshed inside the container (run `aws sso login` on the host). `credential_process` profiles run their host command inside the container, where it usually does not exist.
- ACP `readTextFile` confinement is check-then-read (realpath, then read), so a path swapped in between can escape (TOCTOU). The ACP agent is a local process that can read files itself, so this is a policy guard, not a security boundary; a proper fix needs openat-style fd-relative resolution, which Node lacks.
- grok billing is native only: there is no `--billing` support, so a grok subscription (OAuth) limit is not retried on `XAI_API_KEY` the way claude/codex fall back to their APIs.
- A host `GROK_HOME` override is not seeded into Docker or Modal: seeding always reads `~/.grok/config.toml`, so settings kept only under a custom `GROK_HOME` do not reach the container.
- grok MCP servers that use OAuth do not work in Docker or Modal: `mcp_credentials.json` is not seeded because, like grok's own `auth.json`, it holds refresh tokens that rotate on use (xai-grok-mcp `credentials.rs`), so a container refresh would invalidate the host's copy.
- grok tmux `--allow read-only` is weaker than one-shot: the TUI ignores the headless-only `--tools`, so it relies on `--permission-mode default` plus `--deny Bash --deny Edit --deny MCPTool` rules; any other mutating tool family grok adds later is not covered. `kill_command_or_subagent` cannot be denied by rule: grok classifies it as a path-less Read access (xai-grok-tools/src/permission_access.rs), which only a tool-wide `--deny Read` would match.
- `GROK_AUTH_PROVIDER_COMMAND` makes `--check` report grok `oauth`, but it is not forwarded to Docker or Modal (containers authenticate only with `XAI_API_KEY`/`GROK_CODE_XAI_API_KEY`), so `--check` can show auth that a container run will refuse.
- The grok container-auth check cannot see a key passed through `--docker-arg`, baked into a custom `--docker-image`/`--modal-image`, or held in a `--modal-secret`, so any of those skips it; if the key is not actually there, the run fails inside the container with grok's own "Not signed in" error instead. `cron add` checks the environment at add time, not the cron daemon's environment at run time.
- `grokHome` (and so grok auth detection and transcript lookup) uses `HOME` and ignores `USERPROFILE` on Windows, following the repo-wide `env.HOME` convention, whereas grok itself uses `USERPROFILE` there.
- grok one-shot `--allow read-only` is the only grok mode without `--trust`, so it skips the project's AGENTS.md, skills, hooks and MCP/LSP servers; every tmux session and every one-shot yolo run persists a folder-trust grant in grok's trust store.
- grok session directories for cwds whose URL encoding exceeds 255 bytes are named `<slug>-<blake3>`; Headless matches them by their `.cwd` file instead of computing blake3, and resolves a pinned session id by scanning every cwd directory.
- grok usage fallback cannot price the model grok actually reports: runs bill as `grok-4.6-build`, which models.dev (2026-11-05) does not list, and neither its `grok-4.6` nor `grok-build-0.1` list price reproduces grok's native cost, so a run whose native cost grok withholds (partial) reports `pricingStatus: missing` instead of a guessed estimate. Real streaming-json and `updates.jsonl` recordings are in `tests/fixtures/grok`; a grok Docker run is still unverified.
- `src/cli.ts` (~5,400 lines, `runCli` alone ~1,600) could be split into parsing, dispatch and per-backend modules around the process-tree and owner-lock helpers. A pure move, deferred because it fixes no bug and risks untested breakage.
- `src/root-toml.ts` treats an escaped `\"""` inside a multiline basic string as the closing delimiter (on both the opening-line and closing-line checks), so example assignments after it can be read as root settings. Affects Codex billing inspection and profile model reporting.
- Codex profile model reporting (`readCodexProfileModelSelection` in `src/codex-profile.ts`) reads only the profile file and the root `<CODEX_HOME>/config.toml`, not trusted project-scoped `<workdir>/.codex/config.toml` layers that Codex applies after the profile, so a project-level `model` override is reported and priced as the profile's model. Possible fix: honour project layers, or take the model identity from Codex's own output.
