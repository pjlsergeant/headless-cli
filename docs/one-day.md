# One Day

Known non-show-stopper issues in process lifecycle handling, kept for later.

- Ctrl-Z: the agent's own session makes its group orphaned, so a forwarded SIGTSTP (`src/cli.ts:2316`) is discarded by the kernel for agents without a SIGTSTP handler.
- New-session and double-fork escapes: descendants that leave via a new session and are reparented before headless looks are not cleaned up. Verified: Claude Code's Bash tool starts commands in a new session. Same for setsid, `tmux new-session -d`, pm2. Possible fix: a Linux subreaper supervisor (`PR_SET_CHILD_SUBREAPER`) so orphans reparent to headless.
- Window between `spawn()` and writing `agent.pgid` (`src/cli.ts:2080`): a SIGKILL of headless there (or a failed write) leaves the agent's group unknown to cron.
- A signal inside the billing/retry wrapper after an attempt finishes but before `runWithBilling` returns (`src/cli.ts:4937`) still ends headless immediately, skipping wrap-up.
- Node drops queued stdout data on exit when stdout is a socket pair (Node `spawn` pipes) and the reader is slow; affects Node consumers of `--sdk-format ndjson`, not real pipes (Python SDK).
- Docker runs only clean up the host-side `docker` client tree; processes the agent leaves inside the container are not touched.
- Modal runs: post-exit cleanup and `--keep-background` are no-ops (the agent runs remotely).
- Async run messages (`run message --async`) always clean up the node's tree; a node's stored `--keep-background` is ignored there (`src/async-run-message.ts:216`).
- Run and node store locks (`src/run-storage.ts`) still use proper-lockfile's mtime staleness: two waiters that both see a stale lease can both reclaim it. Not moved onto `src/owner-lock.ts` because node locks hand ownership to another process tree and judge liveness by that tree, which the owner lock does not model.
- Lock directories (`~/.headless/launch-locks/<key>`, `cron/locks/jobs/<id>`) are never removed, by design (removing one would break atomic reclaim); `cron rm` leaves its small lock directory behind.
- Lock holders on another host (shared filesystem) count as alive indefinitely; a crashed remote holder needs its lock directory removed by hand.
- A Docker session's store lock lives in the container-writable session home, so the container can make that session's store writes time out.
- The session store drops records that fail validation the next time it is written (now for the local store too, not only Docker session stores).
- Cron reconcile can mark an execution `killed`/`stale` when the post-exit sweep of its agent group outlasts a daemon tick, though it had finished normally.
- A daemon tick already in progress at shutdown can start an execution after the shutdown kill passed that job; the next daemon's reconcile cleans it up.
- `cron stop` sends SIGTERM and returns without waiting for the daemon to exit.
- Two containers sharing a volume with the same explicitly set hostname and overlapping PIDs can misjudge a live lock holder as stale (`src/owner-lock.ts` host check).
- The Docker session lock is acquired before the wrap-up guard is installed (`src/cli.ts` `acquireDockerSessionLock` vs `installWrapUpGuard`), so a signal in that window skips its release; the holder is on the host, so the lock is reclaimable, not wedged.
- Locks with a maximum hold (session store, cron jobs: 60s; launch: 10 min or `--timeout` + 1 min) can be taken over from a holder that is alive but slower than that. Sections check `held()` before each write, which leaves only the window between that check and the rename; a tmux claim with no `--timeout` that takes over 10 minutes can be overtaken and lose transcript attribution.
- A container started outside headless (so without `HEADLESS_IN_CONTAINER=1`) that mounts `~/.headless` can still take, and on dying wedge, the cron daemon lock or a Docker session lock, which have no maximum hold time.
- Flaky under full-suite load: "Antigravity usage overlay ... SIGTERM handler" test (tests/headless.test.ts) failed once in a full run, passes alone and in later full runs; timing-sensitive.
- Docker launch options (`--docker-image`, `--docker-arg`, `--docker-env`) are not persisted per node, so a host-side `run message` to a Docker or Modal node is refused instead of relaunching it in its sandbox; only a running Docker node's mailbox can start one (with its own flags).
- Nodes a container starts through its mailbox are detached and outlive the requesting container, like host `run message --async`; nothing stops them when the orchestrator exits without `run wait`.
- Explicit `--docker-env NAME=value` entries are handed to nodes started from a mailbox on the detached child's argv (visible in `ps`), as they already were for the original invocation.
- A container can leave dot-prefixed files in its mailbox `requests/` (treated as in-progress writes), using disk in the run dir until that launch directory is swept.
- Two concurrent launches of the same Docker run node get separate mailbox directories; a later launch may sweep the other's directory while it is still polling. (Concurrent launches of one node are already unsupported.)
- User-supplied `--docker-arg` volume mounts are not checked for overlap with Headless state.
- Flaky under full-suite load: "cron daemon keeps its signal handlers until active executions are killed" (tests/cron.test.ts) failed once in a full run, passes alone; timing-sensitive.
- Attacker-filled old mailbox launch directories can linger: the bounded best-effort sweep on the next launch does not recurse into subdirectories a container nested inside its mailbox.
- Prompts starting with "-" are still passed as a bare positional (or `-p` value) to Cursor (`agent`, one-shot and interactive), OpenCode (`run` and interactive run), Pi (one-shot and interactive), Gemini interactive, and Antigravity (`agy -p`); none of these CLIs is installed here to verify whether they accept `--` or a dash-leading value, and none has a stdin prompt path in Headless. Claude, Codex and Gemini one-shot are fixed.
- Gemini one-shot now sends inline prompts on stdin with `--prompt ''` (the path prompt files already used); not verified against an installed gemini.
- Modal sandbox lifetime is counted from sandbox creation (agent timeout + 120s recovery window), so a slow upload eats into the recovery window.
- `--modal-keep-sandbox` creates the sandbox with a 24h lifetime for every run, so if Headless itself is SIGKILLed the sandbox bills up to 24h instead of the agent timeout.
- The kept-sandbox message points at the Modal dashboard or the JS SDK to terminate; Headless has no command to terminate (or fetch from) a kept sandbox.
- ACP SDK logs "Error handling request" to stderr for each refused ACP file read (SDK console logging of handler errors).
- ACP `fs/read_text_file` ignores the request's `line`/`limit` and returns the whole file.
- AWS profile filtering (Docker and Modal) skips `~/.aws/credentials`/`config` when they are symlinks, drops `source_profile` chains and the SSO token cache (`~/.aws/sso/cache`), so SSO or chained profiles need credentials supplied another way in the container.
- `--docker --print-command` prints an AWS mount source in a staged temp dir that is removed when Headless exits, so the printed command is not runnable as is when `AWS_PROFILE` is forwarded.
- The staged Docker AWS credentials temp dir is left behind if Headless is killed without running its cleanup (e.g. SIGKILL).
